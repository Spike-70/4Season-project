## 1. 왜 문서가 이렇게 많은가요

여러분이 쓴 **PRD(제품 요구사항 문서)** 는 "무엇을 만들 것인가"를 적은 문서입니다. 하지만 개발자가 PRD만 보고 바로 코드를 쓸 수는 없습니다. 그 사이에 **"어떻게 만들 것인가"** 를 정하는 단계가 필요합니다.

집을 짓는 상황에 비유하면 이렇습니다.

| 건축 | 소프트웨어 | 이 프로젝트의 문서 |
| --- | --- | --- |
| "방 3개, 화장실 2개인 집을 원해요" | 제품 요구사항 | PRD.md |
| 어디에 무엇을 보관할지 정한 수납 설계도 | 데이터 저장 구조 | DATABASE-MODEL.md |
| 방과 방 사이를 어떤 문으로 어떻게 연결할지 | 화면과 서버가 대화하는 규칙 | API-SPEC.md |
| 벽지·조명·손잡이의 통일된 규격 | 화면의 시각 규칙 | DESIGN-SYSTEM.md |
| 배관·전기 등 눈에 안 보이는 설비 배치 | 서버 내부 구조 | BACKEND-ARCHITECTURE.md |
| 실제 사람이 사는 공간의 동선 설계 | 화면 쪽 구조 | FRONTEND-ARCHITECTURE.md |

**문서를 나눈 이유**는 각 문서를 담당하는 사람이 다르고, 바뀌는 속도도 다르기 때문입니다. 화면 색상이 바뀐다고 데이터 저장 방식이 바뀌지는 않아야 합니다. 문서가 하나로 뭉쳐 있으면 한 곳을 고칠 때마다 전체를 다시 검토해야 합니다.

## 2. 다섯 문서가 각각 무엇을 정하는가

### 2.1 데이터베이스 모델 — "무엇을 어떻게 저장할 것인가"

사용자가 일지를 쓰면 그 글이 어딘가에 저장되어야 합니다. 그 "어딘가"의 구조를 정한 문서입니다.

**핵심 질문**: 사용자가 매수 기록을 남겼을 때, 종목·수량·가격·날짜·그때의 기분·되돌아볼 조건을 각각 어디에 어떤 형태로 담을 것인가?

> **해설판**: [01-DATABASE-MODEL-GUIDE.md](./01-DATABASE-MODEL-GUIDE.md)

### 2.2 API 명세 — "화면과 서버가 주고받는 말"

앱 화면(스마트폰에 보이는 것)과 서버(데이터를 보관하고 계산하는 컴퓨터)는 서로 다른 곳에 있습니다. 둘이 대화하려면 정해진 형식이 필요합니다.

**핵심 질문**: 화면이 "이 사용자의 계좌 상태를 알려줘"라고 물으면, 서버는 어떤 형식으로 답할 것인가?

> **해설판**: [02-API-SPEC-GUIDE.md](./02-API-SPEC-GUIDE.md)

### 2.3 디자인 시스템 — "화면의 규격표"

버튼 색, 글자 크기, 여백을 매번 새로 정하면 화면마다 조금씩 달라집니다. 미리 규격을 정해두는 문서입니다.

**핵심 질문**: 수익률을 표시할 때 빨간색은 몇 번 빨강이고, 글자 크기는 몇이며, 기준일은 어디에 얼마나 작게 붙이는가?

> **해설판**: [03-DESIGN-SYSTEM-GUIDE.md](./03-DESIGN-SYSTEM-GUIDE.md)

### 2.4 백엔드 아키텍처 — "서버 내부를 어떻게 나눌 것인가"

서버가 하는 일은 많습니다. 로그인 처리, 계좌 계산, 알림 발송, 리포트 생성. 이것들을 어떻게 나누어 정리할지 정한 문서입니다.

**핵심 질문**: 4개 계좌를 계산하는 코드는 어디에 두고, 매매 기록을 저장하는 코드와 어떻게 분리할 것인가?

> **해설판**: [04-BACKEND-ARCHITECTURE-GUIDE.md](./04-BACKEND-ARCHITECTURE-GUIDE.md)

### 2.5 프론트엔드 아키텍처 — "화면 쪽을 어떻게 나눌 것인가"

화면도 마찬가지입니다. 홈, 종목 상세, 일지 작성, 결산 등 수십 개 화면을 어떻게 정리할지 정한 문서입니다.

**핵심 질문**: '되돌아볼 조건'을 보여주는 부품은 어디에 두고, 그것을 쓰는 화면 세 곳에서 어떻게 재사용할 것인가?

> **해설판**: [05-FRONTEND-ARCHITECTURE-GUIDE.md](./05-FRONTEND-ARCHITECTURE-GUIDE.md)

## 3. 꼭 알아야 할 기초 용어 20개

문서 전체에 반복해서 나오는 말들입니다. 이것만 알면 대부분 읽힙니다.

### 3.1 시스템의 큰 구조

| 용어 | 뜻 | 이 프로젝트에서 |
| --- | --- | --- |
| **클라이언트 / 프론트엔드** | 사용자 눈앞에 보이는 부분. 스마트폰 화면 | React로 만든 웹 앱 |
| **서버 / 백엔드** | 보이지 않는 곳에서 데이터를 보관하고 계산하는 컴퓨터 | AWS Chalice로 만든 프로그램 |
| **데이터베이스(DB)** | 데이터를 보관하는 창고 | PostgreSQL |
| **API** | 화면과 서버가 대화하는 창구와 그 규칙 | "계좌 상태 알려줘" 같은 요청 목록 |
| **요청(Request) / 응답(Response)** | 화면이 서버에 묻는 것 / 서버가 답하는 것 | |
| **배치(Batch)** | 정해진 시각에 자동으로 도는 작업 | 매일 저녁 6시에 시세를 받아오는 작업 |

**한 장면으로 이해하기**

사용자가 앱에서 "내 계좌" 화면을 엽니다.

```
[스마트폰 화면]  ──① "이 사용자 계좌 상태 줘" (요청) ──▶  [서버]
                                                            │
                                                            ② 창고에서 꺼냄
                                                            ▼
                                                        [데이터베이스]
                                                            │
[스마트폰 화면]  ◀── ③ "총액 3,124만, 수익률 +4.1%" ──────┘
      │
      ④ 그 숫자를 예쁘게 그려서 보여줌
```

- ①③의 **형식**을 정한 것이 API 명세
- ②의 **창고 구조**를 정한 것이 데이터베이스 모델
- ④의 **그리는 규칙**을 정한 것이 디자인 시스템
- ②③을 처리하는 **서버 내부 정리 방법**이 백엔드 아키텍처
- ①④을 처리하는 **화면 내부 정리 방법**이 프론트엔드 아키텍처

### 3.2 데이터베이스 용어

| 용어 | 뜻 | 비유 |
| --- | --- | --- |
| **테이블(Table)** | 같은 종류의 데이터를 모아둔 표 | 엑셀의 시트 하나 |
| **컬럼(Column) / 필드** | 표의 세로 칸. 항목 이름 | '종목명', '수량' 같은 열 제목 |
| **행(Row) / 레코드** | 표의 가로 줄. 데이터 한 건 | 매매 기록 한 건 |
| **기본키(PK, Primary Key)** | 각 행을 구분하는 고유 번호 | 주민등록번호 같은 것 |
| **외래키(FK, Foreign Key)** | 다른 표의 행을 가리키는 연결선 | "이 매매는 3번 사용자의 것" |
| **인덱스(Index)** | 빨리 찾기 위한 색인 | 책 뒤의 찾아보기 |
| **제약(Constraint)** | 넣으면 안 되는 값을 막는 규칙 | "수량은 0보다 커야 함" |

### 3.3 이 프로젝트에서 계속 나오는 개념

| 용어 | 뜻 |
| --- | --- |
| **파생 데이터** | 다른 데이터로부터 계산해서 만든 값. 원본이 바뀌면 다시 계산할 수 있음 |
| **원본 데이터** | 사용자가 직접 입력한 것. 다시 만들어낼 수 없음 |
| **리플레이(Replay)** | 원본 데이터를 처음부터 다시 훑어 계좌 상태를 다시 계산하는 것 |
| **멱등성(冪等性)** | 같은 작업을 두 번 해도 결과가 한 번 한 것과 같은 성질 |
| **캐시(Cache)** | 자주 쓰는 값을 미리 계산해 옆에 놔두는 것 |
| **마이그레이션(Migration)** | 데이터베이스 구조를 바꾸는 작업과 그 기록 |
| **열거형(Enum)** | 정해진 값 중 하나만 들어갈 수 있는 항목. 예: 매수/매도 |

**멱등성이 왜 중요한가**: 사용자가 '저장' 버튼을 눌렀는데 통신이 끊겨서 다시 눌렀다고 합시다. 멱등성이 없으면 매매가 두 번 기록됩니다. 그러면 사용자는 "잘못 기록됐어요"라고 문의하게 되고, PRD 3.5가 줄이려는 문의가 늘어납니다.

## 4. 문서를 읽을 때의 요령

### 4.1 표는 전부 읽지 않아도 됩니다

설계 문서에는 컬럼 목록 같은 긴 표가 많습니다. 이런 표는 **개발자가 구현할 때 참조하는 부품 목록**이라서, 기획자는 표의 존재만 확인하고 넘어가도 됩니다.

| 꼭 읽어야 할 것 | 넘어가도 되는 것 |
| --- | --- |
| 각 절의 첫 문단 (무엇을 정하는지) | 컬럼별 데이터 타입 (`VARCHAR(32)` 같은 것) |
| **굵게** 표시된 문장 | 인덱스 이름 |
| `>` 인용 블록 (이유 설명) | 제약 이름 |
| "왜 이렇게 했는가" 설명 | 파일 경로 목록 |

### 4.2 `>` 로 시작하는 인용 블록이 가장 중요합니다

설계 문서에서 인용 블록은 대부분 **"왜 이렇게 정했는가"** 를 설명합니다. 이 부분이 기획 의도와 어긋나면 지금 바로잡아야 합니다. 코드를 쓴 뒤에는 고치는 비용이 훨씬 커집니다.

### 4.3 PRD 번호가 계속 인용됩니다

`(PRD 7.9)` 같은 표시는 "이 설계는 PRD 7.9절의 요구사항 때문에 이렇게 됐다"는 뜻입니다. 설계가 마음에 안 들면 PRD의 그 절을 함께 보세요. 대부분은 PRD에서 이미 결정한 사항의 결과입니다.

### 4.4 영어 용어는 대부분 그대로 씁니다

`account`, `trade`, `cycle` 같은 단어는 실제 코드와 데이터베이스에서 쓰는 이름이라 번역하지 않습니다. 대신 해설판에서 매번 한국어 뜻을 붙여두었습니다.

## 5. 이 설계에서 가장 중요한 결정 5가지

문서를 다 읽지 못하더라도 이것만은 알아두시면 좋습니다. 나중에 "왜 이렇게 만들었지?"라는 의문이 생길 때 대부분 여기에 답이 있습니다.

### 결정 1 — 4개 계좌를 똑같은 구조로 저장한다

규칙 투자·자유 투자·내 계획대로·그냥 둔 계좌를 **각각 다른 방식으로 만들지 않고, 하나의 틀에 종류 표시만 다르게** 해서 저장합니다.

**왜**: 네 계좌를 비교하는 것이 이 제품의 핵심인데, 저장 방식이 다르면 비교 계산이 계좌 수만큼 복잡해집니다. 또 나중에 규칙 계좌를 하나 더 늘리고 싶을 때(PRD 19.1) 구조를 갈아엎지 않아도 됩니다.

### 결정 2 — 계좌 값은 저장하지 않고 매번 다시 계산할 수 있게 한다

사용자가 입력한 매매 기록은 그대로 보관하고, **계좌 잔고와 수익률은 그 기록으로부터 다시 만들어낼 수 있는 형태**로 둡니다.

**왜**: PRD 3.5는 사용자가 잘못 기입한 매매를 스스로 고칠 수 있어야 한다고 했습니다. 3월 매매를 고치면 그 이후 모든 계좌 값이 달라집니다. 다시 계산할 수 없는 구조라면 운영자가 손으로 고쳐야 하고, 그러면 1인 운영이 불가능해집니다.

또 PRD 19.7은 "계산 방식이 바뀌면 과거 데이터를 새 기준으로 다시 계산할 수 있어야 한다"고 요구합니다. 이건 나중에 추가할 수 없는 성질이라 처음부터 이렇게 만들어야 합니다.

### 결정 3 — 사용자에게 보여줄 문장은 서버가 만든다

"3월 12일에 이렇게 정하셨습니다" 같은 문구를 화면 쪽에서 만들지 않고 **서버가 완성해서 내려보냅니다.**

**왜**: PRD 17장은 서비스가 사용자에게 하는 말을 두 가지 형식으로 엄격히 제한합니다. 문구를 화면 여러 곳에서 각자 만들면 어딘가에서 "지금 파시는 게 좋겠습니다" 같은 문장이 새어 나옵니다. 한 곳에서만 만들면 그곳만 검사하면 됩니다.

**대가**: 나중에 다국어(영어 버전 등)를 지원하려면 서버부터 손봐야 합니다. 이건 의도적으로 감수한 비용입니다.

### 결정 4 — 표시 규칙을 컴퓨터가 강제하게 만든다

"수익률에는 항상 기준일을 붙인다", "비율에는 항상 분모를 붙인다" 같은 PRD 규칙을, 문서에만 적어두지 않고 **어기면 프로그램이 아예 만들어지지 않도록** 설계했습니다.

**왜**: 화면이 50개가 넘어가면 사람이 규칙을 기억해서 지키는 방식은 반드시 새어 나갑니다. PRD 7.9의 기준일 표기와 5.4의 분모 표기는 이 제품의 정직성 요구사항이라 새면 안 됩니다.

### 결정 5 — 바뀔 만한 숫자는 코드에 넣지 않는다

수수료율, 세율, "몇 건 이상이어야 분석을 보여줄지" 같은 값들을 코드가 아니라 **데이터로 저장**합니다.

**왜**: 세율은 법이 바뀌면 바뀌고(PRD 7.7), 기준 건수는 베타 데이터를 보고 조정해야 합니다(PRD 18.8). 코드에 박혀 있으면 값 하나 바꾸는 데 앱 배포가 필요합니다.

## 6. 자주 나올 만한 질문

**Q. 문서에 나온 대로 만들면 얼마나 걸리나요?**
이 문서들은 "무엇을 만들지"를 정한 것이고 일정은 별도로 산정해야 합니다. 다만 문서가 상세할수록 개발 중 되돌아가는 일이 줄어듭니다.

**Q. 나중에 바꿀 수 있나요?**
대부분 바꿀 수 있습니다. 다만 **데이터베이스 모델의 결정 2(재계산 가능한 구조)** 와 **결정 3(서버가 문구 생성)** 은 나중에 바꾸기가 매우 어렵습니다. 이 두 가지는 지금 확인해두시는 게 좋습니다.

**Q. PRD의 미결 사항(18장)은 어떻게 됐나요?**
13건 모두 PRD의 권장안대로 확정했습니다. 다만 나중에 마음이 바뀔 수 있는 값(수수료율, 기준 건수 등)은 결정 5에 따라 설정으로 빼두었으니 언제든 바꿀 수 있습니다. 자세한 목록은 [데이터베이스 모델 해설판 §2](./01-DATABASE-MODEL-GUIDE.md)에 있습니다.

**Q. 개발자에게 이 문서를 그대로 주면 되나요?**
원본 5종을 주시면 됩니다. 해설판은 기획 측에서 검토하실 때 쓰는 용도입니다.

**Q. 뭘 먼저 검토해야 하나요?**
아래 순서를 권합니다.

| 순서 | 문서 | 확인할 것 |
| --- | --- | --- |
| 1 | API 명세 해설판 | 화면에서 필요한 정보가 다 준비되는지 |
| 2 | 디자인 시스템 해설판 | 문구 규칙과 표시 규칙이 PRD 의도와 맞는지 |
| 3 | 데이터베이스 모델 해설판 | 남기고 싶은 기록이 빠지지 않았는지 |
| 4 | 프론트엔드/백엔드 해설판 | 훑어보는 정도로 충분 |

---

## 7. 해설판을 읽는 방법

각 해설판은 원본과 같은 순서로 진행되며, 아래 표시를 씁니다.

| 표시 | 뜻 |
| --- | --- |
| **[원문]** | 원본 문서에 있는 내용을 그대로 가져온 부분 |
| **[쉽게 말하면]** | 앞의 내용을 일상어로 바꾼 설명 |
| **[왜 이렇게 했나]** | 이 결정의 이유. PRD 어느 부분 때문인지 |
| **[기획자가 볼 곳]** | 기획 의도와 어긋날 수 있어 확인이 필요한 부분 |
| **[넘어가도 됩니다]** | 개발자용 내용. 읽지 않아도 무방 |

원본 문서를 옆에 띄워두고 대조하며 읽으면 가장 좋지만, 해설판만 읽어도 전체 그림은 파악되도록 썼습니다.
