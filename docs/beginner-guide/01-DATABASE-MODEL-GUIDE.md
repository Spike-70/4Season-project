## 이 문서가 정하는 것

사용자가 남긴 모든 기록 — 매매, 일지, 깨달은 것, 수칙 — 을 **어떤 서랍에 어떤 형태로 넣을지** 정한 문서입니다.

**[쉽게 말하면]** 커다란 캐비닛을 짜는 설계도입니다. 서랍이 몇 개이고, 각 서랍에 무엇을 넣고, 서랍끼리 어떻게 연결되는지를 정합니다. 서랍을 잘못 짜면 나중에 "3년 전 이 종목에 대해 내가 뭐라고 썼더라?"를 찾을 수 없게 됩니다.

**[왜 가장 먼저 만드나]** 화면이나 기능은 나중에 바꾸기 쉽지만, 데이터 구조는 이미 쌓인 데이터가 있으면 바꾸기가 매우 어렵습니다. 집을 다 지은 뒤에 벽 안의 배관을 옮기는 것과 같습니다.

## 1장. 설계 원칙 — 8가지 약속

원본 1장은 이 문서 전체를 관통하는 8개 원칙을 정합니다. 그중 **기획자가 꼭 알아야 할 4개**를 설명합니다.

### 원칙 1 — 입력과 파생을 분리한다

**[원문]** "사용자가 입력한 사실은 원본 테이블에 불변으로 남기고, 계좌 원장·스냅샷·집계 지표는 언제든 재계산 가능한 파생 테이블로 둔다."

**[쉽게 말하면]** 데이터를 두 종류로 나눕니다.

| 종류 | 예 | 성격 |
| --- | --- | --- |
| **원본** | "3월 12일에 삼성전자 10주를 7만원에 샀다"는 사용자의 기록 | 사용자만 만들 수 있음. 지우면 복구 불가 |
| **파생** | "현재 계좌 잔고 3,124만원, 수익률 +4.1%" | 원본으로부터 계산해 만든 값. 언제든 다시 만들 수 있음 |

**[왜 이렇게 했나]** 두 가지 요구사항 때문입니다.

첫째, PRD 3.5는 사용자가 잘못 기입한 매매를 **스스로 고칠 수 있어야** 한다고 정했습니다. 그런데 3월 매매를 고치면 3월 이후의 모든 계좌 값이 달라집니다. 파생 데이터를 다시 계산할 수 없는 구조라면, 사용자가 정정할 때마다 운영자가 수작업으로 계좌를 맞춰야 합니다. 그러면 1인 운영이 무너집니다.

둘째, PRD 19.7은 "계산 방식이 바뀌면 과거 데이터를 새 기준으로 다시 계산할 수 있어야 한다"고 요구합니다.

**[기획자가 볼 곳]** 이 원칙 때문에 **계좌 화면의 숫자는 실시간으로 즉석 계산되지 않고, 매일 저녁 배치가 계산해둔 값을 보여줍니다.** PRD 7.9가 "직전 영업일 종가 기준"을 항상 표기하라고 한 것과 맞물립니다.

### 원칙 2 — 4개 계좌를 같은 구조로 표현한다

**[원문]** "규칙·자유·내 계획대로·그냥 둔 계좌는 `account.account_type`만 다른 동일 스키마다."

**[쉽게 말하면]** 계좌 4개를 위해 표를 4개 만들지 않고, 표 하나를 만들고 "이 행은 어떤 계좌인가"를 표시하는 칸 하나를 둡니다.

```
계좌 표
┌──────┬─────────────┬───────────┬──────────┐
│ 번호 │ 어떤 사이클  │ 계좌 종류  │ 총액      │
├──────┼─────────────┼───────────┼──────────┤
│  1   │ 2026년 사이클│ 규칙 투자  │ 3,050만  │
│  2   │ 2026년 사이클│ 자유 투자  │ 3,124만  │
│  3   │ 2026년 사이클│ 내 계획대로│ 3,340만  │
│  4   │ 2026년 사이클│ 그냥 둔    │ 2,980만  │
└──────┴─────────────┴───────────┴──────────┘
```

**[왜 이렇게 했나]** 표를 4개로 나누면 "네 계좌를 나란히 비교하라"는 이 제품의 핵심 기능이 계좌 수만큼 복잡해집니다. 그리고 PRD 19.1이 언급한 "규칙 세트를 여러 개로 늘리는 확장"을 하려면 표를 새로 만들어야 합니다. 하나의 표에 종류 표시만 다르게 두면 행을 하나 더 추가하면 끝입니다.

### 원칙 4 — 사이클을 넘는 것과 넘지 않는 것을 구조로 구분한다

**[원문]** "계좌·보유·거래는 `cycle_id`에 종속되고, 일지·깨달은 것·수칙·배지·연습 기록은 `user_id`에 직접 매달린다."

**[쉽게 말하면]** PRD 13.3은 매년 계좌는 초기화되지만 기록은 영구히 쌓인다고 정했습니다. 이것을 **연결 구조로 표현**했습니다.

```
사용자 (영구)
 ├── 2026 사이클 ── 계좌·보유·매매      ← 사이클이 끝나면 이 아래는 정지
 ├── 2027 사이클 ── 계좌·보유·매매
 │
 ├── 일지          ← 사이클과 무관하게 사용자에게 직접 붙음
 ├── 깨달은 것      ← 영구 누적
 ├── 투자 수칙      ← 영구 누적
 └── 배지          ← 영구 누적
```

**[왜 이렇게 했나]** 무엇이 승계되고 무엇이 초기화되는지를 **연결선만 보고도 판별할 수 있게** 하기 위해서입니다. "이건 승계되나요?"라는 질문이 나올 때마다 문서를 뒤지는 대신 구조를 보면 됩니다.

### 원칙 7 — 비율을 저장할 때 분자·분모를 함께 저장한다

**[원문]** "비율 컬럼 단독 저장을 금지하고 분자·분모를 각각 저장한다."

**[쉽게 말하면]** "내 계획 지킨 비율 57%"만 저장하는 게 아니라 "7번 중 4번 = 57%"를 통째로 저장합니다.

**[왜 이렇게 했나]** PRD 5.4가 정한 규칙 때문입니다. 분모가 3인 57%와 분모가 100인 57%는 전혀 다른 이야기인데, 비율만 저장하면 나중에 구분할 수 없습니다. PRD는 "규칙 실행 확인율은 항상 'n회 중 m회'로 분모를 함께 표시한다"고 명시했습니다. 표시 규칙을 지키려면 데이터부터 그렇게 있어야 합니다.

## 2장. PRD 미결 사항을 어떻게 확정했나

PRD 18장에는 "아직 결정하지 못한 것" 14가지가 있었습니다. 설계를 하려면 이것들을 정해야 해서, **전부 PRD의 권장안대로 확정**했습니다.

**[기획자가 볼 곳]** 아래가 확정된 내용입니다. 마음이 바뀐 것이 있으면 지금 말씀해주세요.

| PRD | 무엇을 정해야 했나 | 확정 | 나중에 바꾸기 |
| --- | --- | --- | --- |
| 18.3 | 정기 조정일을 언제로 할지 | 분기별 선물·옵션 만기일 다음 거래일 | **쉬움** (설정값) |
| 18.4 | 종목 선정 근거를 어디까지 공개할지 | 배제 규칙만 공개, 개별 종목 사유는 제공 안 함 | **어려움** (그런 칸을 아예 안 만듦) |
| 18.5 | 늦게 가입한 사람의 시작 종목 수 | 남은 조정 3/2/1/0회 → 10/8/6/4개 | **쉬움** (설정 표) |
| 18.6 | 조정을 한 번도 못 겪는 사람 | '맛보기 사이클'로 표시하고 요약 리포트 제공 | **보통** |
| 18.7 | 수칙 후보를 어떻게 만들지 | 미리 만든 문장 틀에 숫자만 끼워 넣기 | **보통** |
| 18.8 | 분석을 보여줄 최소 건수 | 3건 (설정으로 관리) | **매우 쉬움** |
| 18.9 | 수칙을 지켰는지 판정 | 사용자가 탭으로 표시. 자동 판정은 가능한 것만 | **보통** |
| 18.11 | 자기 보고 조건의 측정 편향 | 자기 보고 비중을 지표로 보여주고 안내 | **쉬움** |
| 18.12 | 로그인 수단 | 카카오만. 나중에 추가할 수 있게 구조만 준비 | **보통** |

**[해설]** "나중에 바꾸기" 칸이 중요합니다.

- **매우 쉬움/쉬움**: 데이터베이스의 설정 값 하나만 고치면 됩니다. 앱을 새로 배포할 필요도 없습니다.
- **보통**: 코드를 고치고 배포해야 합니다.
- **어려움**: 이미 쌓인 데이터를 옮기는 작업이 필요합니다.

18.4가 "어려움"인 이유는 특별합니다. 개별 종목의 선정 사유를 저장하는 **칸 자체를 만들지 않았습니다.** PRD 17.1은 "올해 유망한 30개를 골랐습니다" 같은 표현을 금지하는데, 사유를 저장하는 칸이 있으면 언젠가 그것이 화면에 노출되고 그 순간 규제 위반이 됩니다. 그래서 **구조적으로 불가능하게** 만들었습니다.

## 3장. 이름과 형식 규약

**[넘어가도 됩니다]** 이 장은 개발자가 이름을 짓는 방식을 통일하기 위한 규칙입니다. 다만 두 가지는 알아두시면 좋습니다.

### 금액을 특별하게 다룹니다

**[원문]** "금액·포인트: `NUMERIC(20, 4)`. 부동소수점을 쓰지 않는다."

**[쉽게 말하면]** 컴퓨터가 소수를 다루는 방식에는 두 가지가 있습니다. 하나는 빠르지만 아주 미세한 오차가 생기고, 다른 하나는 느리지만 정확합니다. **금액에는 정확한 쪽을 씁니다.**

**[왜 이렇게 했나]** 이 제품의 핵심 산출물이 "계획대로 했으면 +14.2%, 실제로는 +3.1%"라는 **뺄셈 결과**이기 때문입니다. 미세한 오차가 여러 번 쌓인 뒤 뺄셈을 하면 오차가 결과에 직접 드러납니다.

### 수량에 소수를 허용합니다

**[원문]** "수량: `NUMERIC(18, 6)`. 3,000만 포인트 균등 배분 시 소수 수량이 필연적으로 발생한다."

**[쉽게 말하면]** 3,000만 포인트를 10종목에 나누면 종목당 300만 포인트입니다. 주가가 72,300원이면 41.49...주가 됩니다. 이걸 41주로 깎으면 남는 돈이 생기고, 그 남는 돈이 종목마다 달라집니다.

**[왜 중요한가]** 네 계좌의 시작 조건이 **완전히 같아야** 비교가 성립합니다(PRD 7.3). 소수점을 버리면 계좌마다 남는 현금이 달라져서, 첫날부터 계좌 간 차이가 0이 아니게 됩니다. 모의투자이므로 소수 주식을 허용하는 것이 자연스럽습니다.

## 4~5장. 서랍을 10개 그룹으로 나눴습니다

원본 4장은 약 50개의 표를 10개 그룹으로 묶습니다.

| 그룹 | 무엇을 담나 | 대표적인 표 |
| --- | --- | --- |
| **A. 사용자** | 계정, 설정, 성향 설문 | `user`, `user_setting` |
| **B. 시장 데이터** | 종목, 시세, 공시, 실적 일정, 달력 | `stock`, `daily_price`, `disclosure` |
| **C. 사이클과 계좌** | 사이클, 4개 계좌, 보유 종목, 거래 원장 | `cycle`, `account`, `account_ledger` |
| **D. 매매와 가설** | 매매 기입, 가설 기록, 조건, 회고 | `trade`, `hypothesis`, `hypothesis_condition` |
| **E. 일지** | 일간·주간·월간 일지, 깨달은 것 | `journal_entry`, `insight` |
| **F. 수칙** | 투자 수칙, 마주침 기록 | `principle`, `principle_encounter` |
| **G. 결산** | 지표, 리포트, 예측, 비상 선언, 회고, 배지 | `cycle_metric`, `cycle_report` |
| **H. 연습 모드** | 시나리오, 플레이 기록 | `practice_scenario`, `practice_session` |
| **I. 알림** | 알림, 기기, 설정 | `notification` |
| **J. 시스템** | 설정값, 배치 이력, 감사 로그 | `system_config`, `audit_log` |

**[해설]** 그룹을 나눈 것은 **폴더로 정리한 것**과 같습니다. 실제 데이터베이스에서는 한 곳에 있지만, 개발할 때 담당 영역을 나누는 기준이 됩니다.

## 6장. 열거형 — "정해진 값만 들어갈 수 있는 칸"

**[쉽게 말하면]** 엑셀의 드롭다운 목록과 같습니다. '매수' 또는 '매도' 둘 중 하나만 들어갈 수 있고, '매숴' 같은 오타는 애초에 들어갈 수 없습니다.

**[기획자가 볼 곳]** 이 목록이 곧 **제품에서 가능한 선택지의 전부**입니다. 빠진 것이 있으면 확인해주세요.

### 특히 중요한 열거형 5개

**① 계좌 종류 (`AccountType`)**

| 값 | 뜻 |
| --- | --- |
| `RULE` | 규칙 투자 계좌 |
| `FREE` | 자유 투자 계좌 |
| `PLAN` | 내 계획대로 계좌 |
| `HOLD` | 그냥 둔 계좌 |

**② 그때 할 일 (`PlannedAction`)**

| 값 | 뜻 |
| --- | --- |
| `SELL_ALL` | 전량 판다 |
| `SELL_HALF` | 절반 판다 |
| `HOLD` | 그대로 둔다 |

**[중요]** 이 세 개에 **기본값이 없습니다.** PRD 9.4는 "서비스가 기본값을 정하면 그것이 곧 권유가 됩니다"라고 했습니다. 사용자가 반드시 직접 골라야 하고, 안 고르면 저장이 거부됩니다.

**③ 조건 도달 후 사용자의 반응 (`TriggerResponse`)**

| 값 | 뜻 |
| --- | --- |
| `FOLLOWED` | 정해 둔 대로 실행 |
| `DEVIATED` | 다시 살펴본 뒤 다르게 행동 |
| `REPLANNED` | 대응을 바꾸고 새 조건 설정 |
| `NO_RESPONSE` | 아무 반응 없음 |

**[해설]** PRD 9.8은 앞의 세 가지가 **모두 정당하다**고 했습니다. 그래서 값 이름에도 좋고 나쁨의 뉘앙스를 넣지 않았습니다. `IGNORED`(무시함) 대신 `DEVIATED`(다르게 행동함)를 쓴 것이 그 예입니다.

**④ 항목별 내역 (`DeviationCategory`)**

| 값 | 뜻 | 짝 |
| --- | --- | --- |
| `SAID_SELL_BUT_HELD` | 판다고 해놓고 안 팔았다 | ↔ 아래 |
| `SAID_HOLD_BUT_SOLD` | 보유한다고 해놓고 팔았다 | ↔ 위 |
| `SOLD_BEFORE_CONDITION` | 조건에 닿기 전에 팔았다 | 없음 |
| `UNPLANNED_ADD_BUY` | 계획에 없던 추가 매수 | 없음 |
| `NO_HYPOTHESIS_BUY` | 갑자기 산 것 | 없음 |
| `FOLLOWED_AS_PLANNED` | 정한 대로 행동했다 | 없음 (긍정 집계) |
| `OTHER` | 나머지 (계산상 잔차) | 없음 |

**[기획자가 볼 곳— 중요]** PRD 7.9는 "항목은 반드시 양방향 대칭이어야 한다"고 했습니다. 그런데 실제로 짝을 이루는 것은 **위의 두 개뿐**입니다. 나머지 셋은 매수나 조기 매도에 관한 것이라 반대말이 존재하지 않습니다.

검토 과정에서 이 점이 발견되어, 설계를 이렇게 정리했습니다.

> 강제해야 할 것은 "모든 항목에 짝이 있어야 한다"가 아니라, **"짝이 정의된 항목은 한쪽만 세거나 표시하면 안 된다"** 이다.

없는 반대말을 억지로 만들면 존재하지 않는 행동 유형을 세게 되어 오히려 통계가 왜곡됩니다. PRD의 의도(파는 쪽만 세면 앱이 "파는 게 정상"이라고 은근히 말하게 된다)는 대칭 쌍 하나를 확실히 지키는 것으로 충족됩니다.

**⑤ 깨달은 것의 태그 (`InsightTag`)**

`BUY_TIMING`(사는 시점), `SELL_TIMING`(파는 시점), `STOCK_PICKING`(종목 고르기), `INFO_JUDGEMENT`(정보 판단), `MY_PSYCHOLOGY`(내 심리), `MARKET_FLOW`(시장 흐름), `UNCLASSIFIED`(분류 안 함)

PRD 10.3이 정한 6개 + 건너뛴 경우입니다.

## 8장. 시장 데이터 표

### `stock` — 종목 마스터

**[해설]** 종목 풀에서 빠져도 **영구 보존**합니다. PRD 10.4가 "지난 사이클 기록도 포함해서 종목별로 모아 볼 수 있어야 한다"고 했기 때문입니다. 2026년 종목 풀에 있던 종목이 2027년에 빠져도, 그 종목에 대해 쓴 기록은 계속 볼 수 있어야 합니다.

### `stock_pool` / `stock_pool_item` — 그 해의 종목 30개

**[기획자가 볼 곳 — 중요]** 원본에 이런 문장이 있습니다.

> 개별 종목의 **선정 사유 컬럼을 두지 않는다.** 컬럼이 존재하면 언젠가 노출되고, 그 순간 PRD 17.1의 마지막 금지 문구를 위반한다. 스키마 수준에서 차단한다.

**[쉽게 말하면]** "왜 이 종목을 골랐는지"를 적는 칸을 **아예 만들지 않았습니다.**

**[왜 이렇게까지 했나]** PRD 18.4에서 "배제 규칙만 공개하고 개별 종목의 선정 사유는 제공하지 않는다"고 정했습니다. 그런데 칸을 만들어두고 "화면에는 안 보여주면 되지"라고 하면, 몇 달 뒤 누군가 "이 정보 있는데 왜 안 보여주지?"라며 화면에 붙이게 됩니다. 칸이 없으면 그럴 수 없습니다.

대신 `note` 칸이 있는데 이건 **운영자 메모 전용**이고 사용자에게 절대 노출되지 않습니다.

### `daily_price` — 일별 시세

시가·고가·저가·종가·거래량을 담습니다.

**[기획자가 볼 곳]** 원본에 이런 설명이 있습니다.

> **고가·저가를 저장하되 판정에 쓰지 않는다.** PRD 7.11-3은 조건 도달을 종가 기준으로만 판정할 것을 요구한다. 고가·저가는 종목 상세 차트 표시 전용이며, 판정 엔진은 `close_price`만 참조한다.

**[쉽게 말하면]** "목표가 대비 15% 하락하면"이라는 조건이 있을 때, 장중에 잠깐 15% 빠졌다가 회복해서 종가는 10% 하락으로 끝났다면 → **조건에 닿지 않은 것으로 봅니다.**

**[왜]** PRD 7.11이 정직성 요구사항으로 정한 것입니다. 하루에 한 번 종가만 수집하는 서비스가 장중 가격으로 판정하면, 사용자가 확인할 수 없는 기준으로 계좌가 움직이게 됩니다.

시가를 저장하는 이유는 PRD 9.1이 "보유 종목의 일별 시가·종가를 항상 표시하여 기입 오류를 방지"하라고 했기 때문입니다.

### `disclosure` — 공시

**[기획자가 볼 곳]** 여기에도 **일부러 만들지 않은 칸**이 있습니다.

> 공시 **발생 사실과 원문 링크만** 저장한다. 본문 컬럼을 두지 않는 것이 설계 의도다.

PRD 15.2가 "본문을 저장하거나 요약·분류하지 않는다"고 했고, "공시 본문을 요약하기 시작하는 순간 이 서비스는 매일 콘텐츠를 만드는 일에 발을 들이게 됩니다"라고 경고했기 때문입니다.

제목·접수번호·시각·링크만 저장합니다. 제목은 원문 그대로이고 가공하지 않습니다.

### `earnings_schedule` — 실적 발표 일정 (검토 중 추가됨)

**[해설]** PRD 15.2는 서비스가 제공하는 '사실'로 세 가지를 들었습니다. 시세, 공시, **실적 발표 일정**. 처음 설계에서 세 번째가 빠져 있어 검토 과정에서 추가했습니다.

여기도 마찬가지로 **날짜만 저장하고 실적 수치나 전망은 저장하지 않습니다.** 수치를 담는 순간 해석 제공에 가까워지고, 컨센서스 같은 데이터는 유료입니다(PRD 15.3-3).

### `trading_calendar` / `cycle_calendar` — 달력

증시가 열리는 날과 그 해의 정기 조정일 3개·결산일 1개를 담습니다.

**[해설]** 조정일은 사람이 정하지 않고 **"분기별 선물·옵션 만기일 다음 거래일"이라는 공개 규칙으로 자동 계산**됩니다(PRD 18.3). 운영자는 계산된 결과가 맞는지 연 1회 30분 확인만 합니다.

## 9장. 사이클과 계좌 — 가장 중요한 부분

### `cycle` — 사이클

**[기획자가 볼 곳]** 이 표에 **시작 시점의 조건을 통째로 복사해서 저장**하는 칸들이 있습니다.

| 칸 | 담는 것 |
| --- | --- |
| `remaining_rebalance_count` | 시작할 때 남아 있던 정기 조정 횟수 (3/2/1/0) |
| `initial_symbol_count` | 시작 종목 수 (10/8/6/4) |
| `is_taster` | 조정 0회인 '맛보기 사이클'인가 |
| `settlement_date` | 결산일 |

원본의 설명입니다.

> 시작 시점에 **확정해 저장**한다. 계산으로 유도하면 사용자가 온보딩 중 이탈했다가 조정일이 지난 뒤 복귀했을 때 값이 달라진다 (PRD 14.3).

**[쉽게 말하면]** "지금 남은 조정 횟수"를 매번 계산하지 않고, 시작할 때 한 번 계산해서 적어둡니다.

**[왜]** 3월 14일에 종목을 고르고 앱을 닫았다가 3월 21일(1차 조정일 다음날)에 돌아왔다고 합시다. 매번 계산하는 방식이라면 남은 조정이 3회에서 2회로 줄어들고, 시작 종목 수도 10개에서 8개로 바뀌어야 합니다. 그러면 이미 고른 10개 종목이 무효가 됩니다.

**[해설]** 다만 아직 사이클이 시작되지 않은 상태(`PREPARING`)에서는 다시 계산합니다. PRD 14.3이 "이탈 중에 정기 조정일이 지나가면 다시 들어왔을 때 갱신해 보여주어야 한다"고 했기 때문입니다.

**사이클 상태 5가지**

| 상태 | 뜻 |
| --- | --- |
| `PREPARING` | 종목은 골랐는데 첫 가설 기록을 아직 안 씀 (PRD 14.3) |
| `ACTIVE` | 진행 중 |
| `SETTLING` | 결산 진행 중 |
| `CLOSED` | 결산 완료 |
| `ABANDONED` | 재시작으로 폐기됨 |

### `cycle_stock_selection` — 고른 종목과 그 이유 (검토 중 추가됨)

**[해설]** PRD 16-B4는 종목 선택 단계에서 "종목 선택 + 선택 이유"를 입력받아 "자기 선택의 근거가 기록됨"을 얻는다고 했습니다. 처음 설계에서 이 표가 빠져 있어 추가했습니다.

**[재시작해도 이전 선택을 남깁니다]** PRD 13.4는 재시작하면 계좌를 버리라고 했지 기록을 지우라고 하지 않았습니다. "무엇을 골랐다가 무엇으로 바꿨는가"는 결산에서 좋은 회고 재료입니다.

### `account` — 계좌 4개

**[기획자가 볼 곳 — 매우 중요]**

> **`HOLD` 계좌도 초기 자본 3,000만이다.** 두 실제 계좌 각각과 비교되어야 하므로 6,000만이 아니다 (PRD 7.3). 이 값을 잘못 넣으면 세 개의 차이가 전부 틀어진다.

PRD 7.3의 표를 다시 보면 규칙 투자와 자유 투자에 각각 3,000만씩 총 6,000만을 지급하지만, '그냥 둔 계좌'의 기준은 3,000만입니다. 비교 대상이 각 트랙이기 때문입니다.

### `account_ledger` — 거래 원장 (모든 계산의 원천)

**[쉽게 말하면]** 네 계좌에서 일어난 **모든 사고팔기를 한 줄씩 기록한 장부**입니다. 이 장부만 있으면 계좌 상태를 언제든 다시 계산할 수 있습니다.

한 줄에 담기는 것: 어느 계좌, 어느 종목, 언제, 사기/팔기, 몇 주, 얼마에, 수수료 얼마, 세금 얼마, 그리고 **이 거래가 왜 일어났는가**.

**"왜 일어났는가"의 종류**

| 값 | 뜻 |
| --- | --- |
| `INITIAL_ALLOCATION` | 사이클 시작 시 균등 배분 |
| `USER_TRADE` | 사용자가 기입한 매매 |
| `RULE_REBALANCE` | 정기 조정 규칙에 의한 매도·재분배 |
| `PLAN_EXECUTION` | 조건 도달 시 미리 정한 대응 집행 |
| `SETTLEMENT_LIQUIDATION` | 결산일 전량 매도 |
| `CORPORATE_ACTION` | 거래정지·상장폐지 등에 의한 정리 |

**[기획자가 볼 곳 — 비용 처리]**

> 체결 오차는 **가상 계좌의 조건 집행·조정에만 적용한다** (PRD 7.7). 사용자 기입 매매는 사용자가 적은 가격을 그대로 쓴다. 수수료·세금은 네 계좌 전부에 동일하게 적용한다. **이 순서를 바꾸면 자유 투자가 구조적으로 유리해진다.**

**[쉽게 말하면]** 두 단계로 비용을 붙입니다.

```
1단계: 수수료 + 세금  →  네 계좌 전부에 똑같이
2단계: 체결 오차      →  가상 계좌(규칙·계획·그냥둔)의 자동 집행에만 추가로
```

**[왜]** 현실에서는 "종가에 정확히 팔겠다"고 해도 그 가격에 체결되지 않습니다. 가상 계좌는 종가로 계산하므로 실제보다 유리해집니다. 그래서 불리한 쪽으로 약간 보정합니다. PRD 7.7이 "가상 계좌를 실제보다 좋아 보이게 만들지 않기 위함"이라고 한 부분입니다.

### `rebalance_execution` / `rebalance_confirmation` — 정기 조정과 확인 버튼

**[기획자가 볼 곳 — 설계의 핵심]** 이 둘을 **일부러 다른 표로 분리**했습니다.

> 1:1로 분리하는 이유는 **확인이 계좌 구조에 개입할 수 없음을 스키마로 못 박기 위해서**다. 같은 테이블의 컬럼이었다면 언젠가 조정 로직이 이 값을 읽게 된다.

**[쉽게 말하면]** PRD 7.4·8.5는 "확인 버튼은 계좌를 움직이지 않는다"고 여러 번 강조합니다. 이것을 문서에만 적어두지 않고, **확인 기록을 물리적으로 다른 서랍에 넣어서** 계좌 계산 코드가 그 서랍을 열 이유가 없게 만들었습니다.

**[조정 근거를 함께 저장합니다]**

> `sold_items`에 **선정 근거(구간 수익률과 순위, 동점 처리 사유)를 함께 저장**한다. PRD 8.4·17장 4번이 요구하는 "왜 이 종목이 정리되었는지 사용자가 확인할 수 있느냐"를 사후 재계산 없이 보장하기 위해서다.

나중에 다시 계산하면 시세 데이터가 수정됐을 때 답이 달라질 수 있으므로, 그때의 판단 근거를 그대로 박제합니다.

## 10장. 매매와 가설 기록

### `trade` — 사용자가 기입한 매매

**[해설]** 정정할 때 원본을 덮어쓰지 않고, 원본을 `SUPERSEDED`(대체됨) 상태로 바꾸고 새 기록을 만듭니다. PRD 3.5의 "정정 이력은 남되"를 구현한 것입니다.

**[기획자가 볼 곳]** 밤에 기입했는지 알기 위해 `entered_at`(실제 기입 시각)을 별도로 저장합니다. PRD 7.10의 '심야의 결단' 배지를 위한 것입니다.

### `hypothesis` — 가설 기록

매수할 때 남기는 판단 근거입니다. 논리, 확신도(1~5), 그날의 기분, 예상 보유 기간을 담습니다.

**[기획자가 볼 곳 — 매우 중요]**

> 부분 유니크 인덱스가 PRD 7.6의 "조건은 종목 단위로 하나만 살아 있다"를 **DB 수준에서 강제**한다. 애플리케이션 버그로 조건이 둘 이상 활성화되면 '내 계획대로 계좌'의 우선순위 규칙이 붕괴한다.

**[쉽게 말하면]** 같은 종목을 세 번 나눠 사면 가설 기록이 3개 생기지만, **살아 있는 조건은 항상 하나뿐**이어야 합니다. 이걸 코드로 지키게 하지 않고 **데이터베이스가 직접 막도록** 했습니다. 두 개를 활성화하려고 하면 저장 자체가 거부됩니다.

### `hypothesis_condition` — 조건과 '그때 할 일'

PRD 5.3의 두 칸 구조를 한 줄로 표현합니다.

```
[ 목표가 대비 15% 하락 ] 하면 → [ 전량 판다 ]
        조건 칸                    그때 할 일 칸
```

**[기획자가 볼 곳 — 중요한 설계 결정]**

> **`resolved_threshold_price`를 생성 시점에 확정 저장한다.** "목표가 대비 15% 하락"을 매일 재계산하면 목표가 수정·수정주가 반영 시 판정선이 소리 없이 움직인다. PRD 1.3의 "결과를 알기 전에 판단 근거를 고정"은 판정 기준값 자체에도 적용되어야 한다.

**[쉽게 말하면]** "목표가 대비 15% 하락"이라고 입력하면, 그 순간 **"63,750원 아래로 내려가면"이라는 실제 가격으로 바꿔서 저장**합니다.

**[왜]** 매번 계산하는 방식이면, 나중에 목표가를 수정하거나 주식이 분할되었을 때 판정선이 사용자 모르게 움직입니다. PRD 1.3의 핵심 메커니즘 "① 고정 — 결과를 알기 전에 판단 근거를 고정시켜 둔다"가 무너집니다.

**[두 종류의 조건]**

| 종류 | 예 | 판정 |
| --- | --- | --- |
| `AUTO` (자동 판정) | "목표가 대비 15% 하락" | 매일 저녁 자동으로 확인 |
| `SELF_REPORT` (자기 보고) | "실적 전망이 하향되면" | **사용자가 직접 표시해야 함** |

두 번째가 PRD 18.11이 걱정한 **측정 편향**의 원인입니다. 사용자가 표시하지 않으면 '내 계획대로 계좌'가 집행되지 않고, 결과적으로 "계획과 실제의 차이"가 실제보다 작게 나옵니다. 그래서 자기 보고 조건의 비중을 별도 지표로 저장하고 리포트에 함께 표시합니다.

**서비스가 추정으로 보정하지 않습니다.** PRD 18.11이 세 번째 선택지(추정 보정)를 "서비스가 사용자가 하지 않은 판단을 대신 내리는 것"이라며 명시적으로 배제했기 때문입니다.

### `condition_trigger` — 조건에 닿은 사건

**[해설]** 이 표가 **'내 계획 지킨 비율'의 분모**입니다. 조건에 몇 번 닿았고(분모), 그중 몇 번 정해둔 대로 했는지(분자)를 여기서 셉니다.

### `deviation_event` — 항목별 내역

**[기획자가 볼 곳]**

> `impact_amount`는 **결산 시점에 확정**된다. 사이클 중에는 NULL이거나 잠정치이며, 화면에서는 건수만 보여준다. 진행 중 종목의 기여도를 확정 숫자로 보여주면 PRD 7.11의 정직성 요구를 어기게 된다.

**[쉽게 말하면]** 사이클 중에는 "'판다고 해놓고 안 팔았다' 3건"까지만 보여주고, "그것 때문에 −7.4%p 손해"라는 금액은 결산 때 확정합니다.

**[왜]** 아직 보유 중인 종목의 손익은 계속 변합니다. 오늘 −7.4%p였다가 내일 +2%p가 될 수 있습니다. 확정되지 않은 숫자를 확정처럼 보여주면 사용자가 잘못된 교훈을 얻습니다.

## 11장. 일지와 깨달은 것

### `journal_entry` / `journal_item` — 일지

**[해설]** "오늘 기억할 만한 것 3가지"를 **한 덩어리 글이 아니라 항목 3개로 나눠서** 저장합니다.

**[왜]** PRD 10.3이 "특정 문장을 '깨달은 것'으로 표시"할 수 있어야 한다고 했기 때문입니다. 한 덩어리로 저장하면 그중 한 문장에만 별표를 달 수 없습니다.

**[월간 일지의 시장 수치를 사진 찍어 둡니다]**

> `market_context`를 **스냅샷으로 저장**한다. 사용자가 그때 본 숫자와 나중에 다시 열었을 때의 숫자가 달라지면(수정주가 반영 등) 해석의 근거가 사라진다.

**[쉽게 말하면]** 월간 일지를 쓸 때 "이번 달 지수 −3.2%"를 보고 해석을 적었는데, 나중에 그 숫자가 −3.1%로 바뀌면 사용자의 글이 이상해집니다. 그래서 그때 본 숫자를 함께 저장합니다.

### `insight` — 깨달은 것

**[기획자가 볼 곳 — 좋은 설계]**

> **`content`를 원본 참조가 아닌 사본으로 저장한다.** 사용자가 일지 문장을 나중에 고쳐도 "그때 깨달은 것"은 그 시점의 문장이어야 한다. PRD 1.2의 "기억이 재구성된다"는 문제의식이 데이터에도 적용된다.

**[쉽게 말하면]** 일지에 "조급하게 사면 안 되겠다"고 쓰고 별표를 달았습니다. 나중에 일지를 "천천히 판단하자"로 고쳐도, **깨달은 것 목록에는 원래 문장이 남습니다.**

**[왜]** 이 제품 전체가 "결과를 안 뒤에 기억이 재구성되는 것"과 싸우는 제품입니다. 그 원칙을 데이터 저장 방식에도 적용했습니다.

### `journal_streak` — 기록 연속일

**[기획자가 볼 곳]**

> **끊긴 연속일에 부정적 처리를 하지 않는다.** `current_streak_days`가 0으로 리셋될 뿐이며, 리셋 이벤트를 별도로 기록하거나 알림을 보내지 않는다 (PRD 10.5).

PRD 4.1의 "혼내지 않는다" 원칙이 데이터 구조에까지 반영된 예입니다. "연속 기록이 끊겼습니다" 같은 알림을 보내려면 끊긴 사건을 기록해야 하는데, 그 기록 자체를 남기지 않습니다.

## 12장. 투자 수칙

### `principle` — 수칙

**[기획자가 볼 곳]**

> **수칙은 종목과 연결하지 않는다** (PRD 11.4, 19.2). `stock_id` 컬럼을 두지 않는 것이 명시적 설계 결정이며, 종목 풀이 매년 바뀌므로 종목에 묶인 수칙은 다음 사이클에 쓸 수 없다.

또 하나의 "일부러 만들지 않은 칸"입니다.

### `principle_encounter` — 수칙을 마주친 기록

**[기획자가 볼 곳 — 중요]**

> **`kept`가 NULL 가능해야 한다.** PRD 18.9는 "마주친 횟수 중 표시된 것만"으로 계산하고 그 사실을 명시하라고 요구한다. `false` 기본값을 쓰면 무표시가 곧 위반으로 집계되어 사용자를 부당하게 평가하게 된다.

**[쉽게 말하면]** 수칙이 화면에 나타났을 때 사용자가 "지켰다/안 지켰다"를 탭으로 표시합니다. 그런데 **아무것도 안 누르고 넘어갈 수도 있습니다.** 이 경우를 "안 지킴"으로 세면 안 됩니다.

세 가지 상태가 필요합니다: 지킴 / 안 지킴 / **표시하지 않음**. 그래서 예/아니오만 담을 수 있는 칸이 아니라 "비어 있을 수도 있는" 칸으로 만들었습니다.

### `principle_template` — 수칙 문장 틀

PRD 18.7에서 채택한 "문장 틀 방식"입니다. 미리 만들어둔 문장에 사용자의 숫자만 끼워 넣습니다.

**[기획자가 볼 곳]**

> `counterpart_template_id`가 비어 있는 활성 템플릿은 배포 검증에서 실패 처리한다. 한쪽만 있는 후보 틀은 그 자체로 특정 매매 방향을 권하는 장치가 된다 (PRD 11.4).

**[쉽게 말하면]** "'전량 판다'로 정한 조건에 닿으면 그날 안에 판단을 기록한다"는 수칙 후보를 준비했다면, 반대 방향("'그대로 보유'로 정했으면 조건에 닿아도 하루는 기다린다") 후보도 반드시 함께 준비해야 합니다. 안 그러면 시스템이 배포되지 않습니다.

## 13장. 결산과 지표

### `cycle_metric` — 사이클 지표

**[해설]** 수익률, 세 개의 차이, 두 준수율, 기분별 분석 등 모든 집계값을 담습니다. **칸을 미리 정해두지 않고 "지표 이름 - 값" 형태**로 저장해서, 지표가 늘어나도 표 구조를 바꾸지 않아도 됩니다.

**[기획자가 볼 곳 — 가장 중요한 금지 사항]**

> **`adherence.plan_rate`와 `adherence.rule_confirm_rate`를 합산한 지표를 만들지 않는다.** PRD 5.4가 명시적으로 금지한다. 두 키를 입력으로 받는 파생 지표는 코드 리뷰에서 거부 사유다.

PRD 5.4는 '내 계획 지킨 비율'과 '규칙 실행 확인율'을 절대 하나로 합치지 말라고 했습니다. 분모도 다르고, 낮을 때의 원인도 처방도 다르기 때문입니다. 이것을 **코드 리뷰 규칙으로까지** 못 박았습니다.

**[각 지표에 함께 저장되는 것]**

| 항목 | 왜 |
| --- | --- |
| 분자·분모 | PRD 5.4의 "n회 중 m회" 표시 |
| 표본 수 | 3건 미만이면 해석 문장을 붙이지 않기 위해 (PRD 7.11) |
| 표시 가능 여부 | 위 판정 결과 |
| 기준일 | PRD 7.9 |
| **계산 버전** | 나중에 계산 방식이 바뀌었을 때 구분 (PRD 19.7) |

### `cycle_report` — 올해의 투자 레슨

**[기획자가 볼 곳]**

> **문장이 아니라 데이터를 저장한다.** 표현 문구는 프론트엔드 렌더러가 담당하고 페이로드는 숫자와 참조만 담는다. 문구를 저장하면 톤 정책(PRD 4.1) 변경 시 과거 리포트를 고칠 수 없다.

**[쉽게 말하면]** "이번 사이클 자유 투자 +3.1%, 계획대로 했다면 +14.2%였습니다"라는 **완성된 문장을 저장하지 않고**, 숫자 두 개(+3.1, +14.2)와 "이 형식으로 보여줘"라는 표시만 저장합니다.

**[왜]** 나중에 문구 톤을 바꾸기로 하면, 문장을 저장한 경우 과거 리포트는 옛날 말투로 남습니다. 숫자만 저장하면 전부 새 말투로 다시 그려집니다.

### `cycle_retrospective` — 사이클 회고 (검토 중 추가됨)

**[해설]** PRD 13.1의 결산 6단계 중 3단계 "사이클 회고 작성(표준 포맷, 선택형 위주)"이 처음 설계에서 누락되어 추가했습니다.

**[기획자가 볼 곳 — 중요한 순서]**

> **회고를 리포트보다 먼저 두는 것이 순서상 중요하다.** 리포트의 숫자를 본 뒤에 회고를 쓰면 기억이 숫자에 맞춰 재구성된다 — PRD 1.2가 지목한 바로 그 문제다.

다만 회고를 **강제하지는 않습니다.** 안 쓰고 넘어가도 리포트를 볼 수 있습니다. 강제하면 결산이 막히고, 결산이 막히면 다음 사이클도 막힙니다(PRD 8.6).

### `emergency_declaration` — 비상 선언

**[기획자가 볼 곳]**

> 계좌 스냅샷을 **JSONB 사본으로 저장**한다. 참조만 두면 매매 정정으로 리플레이가 발생할 때 "그때 본 숫자"가 바뀐다. 비상 선언의 학습 가치는 그 시점 인식의 보존에 있다.

**[쉽게 말하면]** 비상 선언을 하면 그 순간의 4계좌 상태를 **사진 찍듯이 통째로 복사해서** 저장합니다.

**[왜]** PRD 8.7은 결산 때 "그때는 세상이 끝날 것 같았는데 아무 일도 아니었다"는 것을 확인시켜주는 게 이 기능의 목적이라고 했습니다. 그때의 숫자가 나중에 바뀌면 그 장면이 성립하지 않습니다.

### `badge_definition` — 배지

**[기획자가 볼 곳]**

> **획득 조건 사전 공개**가 원칙이므로 정의 자체가 사용자 노출 데이터다.

PRD 7.10의 "숨겨진 조건은 두지 않습니다"를 구현한 것입니다. 아직 못 받은 배지도 이름과 조건을 볼 수 있습니다.

또 `DEVIATION` 종류의 배지는 **반드시 대칭 짝이 있어야** 하고, 없으면 배포가 거부됩니다. '존버 장인'만 있고 '마음이 바뀜'이 없으면 배지 체계가 "파는 게 정상"이라고 말하게 되기 때문입니다.

## 14장. 연습 모드

### `practice_scenario` — 시나리오

**[기획자가 볼 곳 — 좋은 장치]**

> 시나리오 풀에 `outcome_class='PLAN_LOSES'`가 최소 1개 이상 활성 상태여야 한다 (PRD 12.3-3). 이 검증은 배포 시 실행하며, 없으면 연습 모드가 "계획대로 하면 항상 이긴다"는 편향된 장치가 된다.

**[쉽게 말하면]** PRD 12.3은 "계획대로 했을 때 오히려 손해인 구간도 넣습니다"라고 했습니다. 이것을 **시스템이 검사**하도록 만들었습니다. 그런 시나리오가 하나도 없으면 배포가 실패합니다.

**[왜]** PRD가 "연습 모드가 매번 '계획대로 했으면 이겼다'로 끝나면 사용자는 이 앱이 자기를 설득하려 한다는 것을 눈치챕니다"라고 경고한 부분입니다.

### `practice_session` — 플레이 기록

**[기획자가 볼 곳]**

> **연습 모드 수익률은 사용자 지표로 노출하지 않는다** (PRD 12.4). 결과 화면의 대조에만 쓰이고, 누적 통계·배지·공유 이미지에는 '미리 정한 대로 한 비율'만 사용한다.

PRD 4.2의 "재미 요소는 기록과 회고에만 붙이고 매매 행위에는 절대 붙이지 않는다"를 지키는 부분입니다. 수익률을 누적 기록으로 만들면 그것이 곧 점수가 되고, 사용자는 점수를 올리려 하게 됩니다.

| 우선순위 | 알림 |

| 1 (최상) | 되돌아볼 조건 도달 |
| 2 | 정기 조정일, 결산일, 다음 사이클 시작 |
| 3 | 주간·월간 회고 |
| 4 | 일지 리마인더 |

**[밀린 알림을 지우지 않습니다]**

> 밀린 알림은 삭제하지 않고 `SUPPRESSED`(밀림)로 남긴다. 인앱 배지로만 표시하는 처리(PRD 10.6)를 위해 존재를 알아야 하고, 알림 정책 튜닝의 근거 데이터가 된다.

## 16장. 시스템 관리용 표

### `system_config` — 바뀔 수 있는 값들

**[기획자가 볼 곳 — 중요]** 여기 들어가는 값은 **앱 배포 없이 바꿀 수 있습니다.**

| 값 | 예 | 왜 여기 있나 |
| --- | --- | --- |
| 수수료율 | 0.015% | 법·정책 변경 (PRD 7.7) |
| 매도 거래세 | 0.18% | 법 개정 |
| 가상 계좌 체결 오차 | 0.1% | 튜닝 필요 |
| 분석 표시 최소 건수 | 3건 | 베타 데이터로 조정 (PRD 18.8) |
| 트랙당 초기 자금 | 3,000만 | |
| 비상 선언 한도 | 2회 | |
| 일지 소급 허용일 | 14일 | |
| 하루 알림 한도 | 1건 | |

**[해설]** 이 값들은 **날짜 구간과 함께** 저장됩니다. 세율이 6월에 바뀌면 5월 거래에는 옛 세율, 7월 거래에는 새 세율이 적용됩니다. 사이클 중간에 법이 바뀌어도 실제와 일치하게 계산됩니다.

### `recompute_job` — 다시 계산 대기 목록

사용자가 매매를 정정하면 여기에 "이 사이클을 이 날짜부터 다시 계산해줘"라는 작업이 등록되고, 5분 안에 처리됩니다.

### `audit_log` — 감사 기록

사이클 재시작, 매매 삭제, 탈퇴, 설정 변경 같은 중요한 작업을 기록합니다. "왜 이 데이터가 없어졌지?"를 추적할 수 있게 합니다.

## 17장. 다시 계산하는 방식

**[쉽게 말하면]** 이 절이 원칙 1의 실제 작동 방식입니다.

```
[원본 데이터]                        [다시 계산]              [파생 데이터]
사이클 설정                              ↓
고른 종목                          ┌──────────┐              거래 원장
사용자 매매 기록          ────▶   │ 계산 엔진 │   ────▶     보유 종목
조건과 그때 할 일                  └──────────┘              일별 성과
일별 시세                                                    지표
비용 설정
```

**[네 계좌가 각각 어떻게 만들어지나]**

| 계좌 | 무슨 일이 일어나나 |
| --- | --- |
| **그냥 둔** | 시작할 때 사고, 결산일에 판다. **그 사이 아무 일도 없음** |
| **규칙 투자** | 시작할 때 사고, 조정일마다 하위 2종목 팔아 나머지에 나누고, 결산일에 전부 판다. **사용자 입력 무시** |
| **자유 투자** | 시작할 때 사고, 사용자가 기입한 대로 사고팔고, 결산일에 전부 판다 |
| **내 계획대로** | 시작할 때 사고, 조건에 닿으면 미리 정한 대응을 집행하고, 결산일에 전부 판다 |

**[언제 다시 계산하나]**

| 사건 | 다시 계산할 범위 |
| --- | --- |
| 매매 정정·삭제 | 그 날짜부터, 자유 투자 계좌만 |
| 조건 재설정 | 재설정일부터, 내 계획대로 계좌 |
| 거래정지·상장폐지 | 발생일부터, 네 계좌 전부 |
| 시세 정정 | 정정일부터, 네 계좌 전부 |
| 계산 방식 변경 | 사이클 시작일부터, 네 계좌 전부 |

**[멱등성 요구]** 같은 작업을 두 번 실행해도 결과가 같아야 합니다. 이걸 자동 테스트로 검증합니다.

## 19~20장. 빨리 찾기와 데이터 삭제

### 인덱스 (빨리 찾기)

**[넘어가도 됩니다]** 데이터가 많아졌을 때 원하는 것을 빨리 찾기 위한 색인 설계입니다.

한 가지만 알아두시면 됩니다. **"이 종목에 대해 내가 쓴 모든 기록 보기"** 는 여러 서랍을 동시에 뒤져야 하는 무거운 조회입니다(PRD 10.4). 그래서 이 기능에 필요한 색인을 특별히 신경 써서 설계했습니다.

### 탈퇴와 삭제

| 단계 | 처리 |
| --- | --- |
| 탈퇴 요청 | 상태만 바꾸고 **바로 지우지 않음** |
| 유예 7일 | 이 기간에 다시 로그인하면 복구 |
| 7일 후 | 배치가 완전 삭제. 모든 관련 데이터가 연쇄적으로 삭제됨 |
| 탈퇴 전 | 내보내기를 한 번 권유 (PRD 13.5) |

**[왜 유예를 두나]** PRD 13.5가 "탈퇴했는데 데이터를 복구해 달라"는 문의가 1인 운영에서 가장 부담스러운 유형이라고 했습니다. 7일 유예 + 내보내기 권유로 대부분 예방됩니다.

## 21장. 구조를 바꿀 때

**[넘어가도 됩니다]** 나중에 표에 칸을 추가하거나 뺄 때의 절차입니다.

한 가지만: **칸을 지울 때는 두 번에 나눠서** 합니다. 먼저 그 칸을 안 쓰도록 프로그램을 바꿔 배포하고, 그다음 릴리스에서 실제로 지웁니다. 한 번에 하면 배포 중 잠깐 프로그램이 없는 칸을 찾게 되어 오류가 납니다.

**[기획자가 볼 곳]** 배지 문구, 조건 선택지, 태그 목록, 수칙 문장 틀 같은 **PRD 3.4의 "최초 1회 작업" 산출물**은 코드가 아니라 데이터로 관리되며, 값을 고치는 것도 정식 배포 절차를 따릅니다. 즉흥적으로 바꿀 수 없고 기록이 남습니다.

## 22장. 나중의 확장에 대한 대비

PRD 19장이 언급한 확장을 지금 구조가 감당할 수 있는지 점검한 표입니다.

| 확장 | 준비 상태 |
| --- | --- |
| 규칙 세트를 여러 개로 (19.1) | 계좌 종류에 값 하나 추가하면 됨 |
| 수칙의 장기 추적 (19.2) | 이미 이력 연결이 있음 |
| 실제 투자 연동 (19.3) | 매매 출처 구분 칸을 미리 만들어둠 |
| 뉴스 수집 (19.4) | 공시와 같은 형태로 표 추가 |
| 종목 풀 자동 선정 (19.5) | 배제 규칙이 이미 데이터로 저장됨 |
| 구독·결제 (19.6) | 새 그룹 추가. 기존 구조 영향 없음 |
| **여러 해 비교 리포트 (19.7)** | **가장 강한 제약. 아래 참조** |

**[기획자가 볼 곳 — 가장 중요]**

> **19.7이 가장 강한 제약을 만든다.** "계산 방식이 바뀌면 과거 데이터를 새 기준으로 다시 계산할 수 있어야 한다"는 요구 때문에, 모든 집계 지표는 (1) 원본 입력으로부터 재계산 가능하고 (2) 계산 버전을 기록하며 (3) 표본 수와 분모를 함께 보존해야 한다. **이 세 조건은 MVP 시점부터 지켜야 하며, 나중에 소급 적용할 수 없다.**

**[쉽게 말하면]** PRD 19.7은 "계획과 실제의 차이가 해마다 줄어드는 것이 이 제품의 가치를 증명하는 유일한 증거"라고 했습니다. 그런데 2년차에 계산 방식을 개선하면, 1년차 데이터를 같은 기준으로 다시 계산해야 비교가 가능합니다.

이걸 나중에 준비할 수는 없습니다. 1년차 데이터를 원본으로부터 다시 계산할 수 있는 형태로 저장해두지 않았다면, 그때는 이미 늦습니다. 그래서 **처음부터** 이렇게 만들었습니다.
